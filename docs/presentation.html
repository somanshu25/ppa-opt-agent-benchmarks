Task 1 · Define hard problems

Four hard problems, and why each is hard in silicon

A PPA agent has three levers — flow knobs, constraints (SDC), and RTL/netlist structure. Every one of them has a degenerate solution that improves the reported numbers while making the chip worse. That is what makes these problems hard, and it is specific to each problem in a different way.

Problem The engineering situation Why it is genuinely hard
HP-A
Constraint integrity		 An SDC is the contract between design intent and what the tools actually optimise. A wrong or incomplete SDC is still valid Tcl and still produces a clean run. Missing constraints mean unchecked paths, and unchecked paths cannot report violations — so a broken SDC often reports better QoR than a correct one. This is how real designs reach tapeout with paths nobody ever timed.
HP-B
Budgeted die-area minimisation		 Die area is money. Every µm² is silicon cost, multiplied by volume. Shrinking the floorplan tightens placement and routing until timing collapses or the flow fails outright. The optimum sits directly beside a cliff, there is no gradient to follow, and each trial is a full RTL-to-GDS run. Finding it in 400 runs is not an industrial answer.
HP-C
QoR regression root-cause		 "Area went up 8% after this commit." Someone has to find out why. A regression surfaces stages away from its cause. A floorplan change presents as a routing-congestion symptom three stages later. Sixteen stage metric sets contain both the causal delta and dozens of inherited ones, and they look identical.
HP-D
Top-level → block budgeting		 In hierarchical design the top-level clock period must be split across blocks and the wires between them. Every block can close timing standalone while the chip fails. The budget is a sum constraint that no individual block can see, and it is zero-sum: giving block A more takes it from B. The defect exists in the relation between artifacts, not in any of them.

Upstream ORFS states HP-D's gap itself, in platforms/asap7/constraints.sdc: "ORFS regression checks do not have the ability to distinguish between timing closure failures (register to register paths) and optimization constraints violations."

Task 1 · Define hard problems

Why coding agents fail at each — and how you'd know they succeeded

Problem Why a coding agent specifically fails How success is measured
HP-A It reads impl.sdc and sees valid Tcl with no defect; then reads QoR saying things improved. Both signals say "fine". The defect is an absence, and there is no test to run that reveals it. Measured on aes: deleting set_input_delay made reported slack improve while the design missed timing by 280 ps. Re-time the agent's layout against a held-out reference SDC. Binary resolve over two assertion sets. Validated exact: given identical constraints, sign-off reproduces the flow's own numbers to the digit on all six timing metrics.
HP-B No ground truth exists — nothing was broken, so "better" is a Pareto judgement, not a pass/fail. LLM agents are poor at sample-efficient search under a hard budget. Measured: search tasks cost ~7× the wall time and ~6× the money of repair tasks, and consumed their entire budget on every attempt. Pareto improvement against a public baseline, with timing and DRC as gates, not scores. Runs consumed reported as a first-class result. Scored against a measured reference optimum, not just "did it improve".
HP-C git log does not help, because the cause is usually a knob or a constraint rather than code. Distinguishing a causal delta from an inherited one is domain knowledge with no textual signature — nothing in the repository teaches it. Stage-attribution accuracy plus cause identification, against ground truth we injected. The cleanest oracle of the four: with bit-exact determinism there is no run-to-run noise, so every delta between two runs is attributable.
HP-D No file contains the bug. Every per-block check passes. An agent trained to make tests pass has nothing to optimise, because the tests already pass — which breaks the SWE-bench shape entirely. Four tiers, cheapest first: budget conservation arithmetic (free, no flow run), per-block closure, integrated top-level STA, then summed block area/power. Gate on closure, score on summed area — otherwise the grader rewards massive over-budgeting.

The common thread: the metric the agent can see is not the metric that matters, and in HP-A it actively points the wrong way. So the scarce artifact is not the optimising agent — it is the grader. The agent is replaceable; the grader is the moat.

Task 2 · Create benchmark tasks

The grader, in one idea borrowed from SWE-bench

SWE-bench faces the identical attack — an agent could edit the tests. Its defence is one line:

git checkout <base_commit> -- tests/

It throws away the agent's copy of the thing that judges it. We do exactly that to constraints.

        agent's layout                        measuring stick
        ─────────────────                     ───────────────
  BUILT WITH:  impl.sdc      ──────────►      JUDGED WITH: golden.sdc
  6_final.odb   netlist + placement + routing   ← unchanged
  6_final.spef  its own extracted parasitics    ← unchanged

Re-time, don't re-run. The layout is frozen; only the ruler changes. Loosening a constraint cannot buy score, because the loosened constraint is not the one used to judge. This mirrors real practice — implementation SDC versus sign-off SDC.

Validated exact — and the self-test earned its keep immediately

With golden == impl, sign-off must reproduce the flow's own numbers. It does, to the digit, on all six timing metrics. The first attempt failed by 4.8 ps and caught a real bug: CTS injects set_propagated_clock, so ideal clocks were being timed against a design with a real clock tree. Without the self-test, that ships as a silently biased gate and every verdict downstream is wrong by a little.

Task 2 · Create benchmark tasks

The synthetic defects: what each one injects, and what it tests

Each class injects exactly one line of change into the constraints, so any difference in the resulting chip is attributable to it and nothing else.

ClassThe one-line mutation What it is designed to test
C1 set clk_period 0.69 → 0.00069
unit slip, ×1/1000
 Unambiguous ground truth — the calibration instance. Tests whether the agent recognises a structural error rather than recalling a value.
C2 set_input_delay … deleted The silent class. Input paths become unconstrained, so the implementation run looks better. Only the held-out sign-off disagrees.
C3 set_output_delay … deleted C2's output-side twin.
C5 set clk_io_pct 0.15 → 0.45 Nothing breaks. The design is simply over-constrained and wastes area and power. Tests QoR judgement, not defect repair.

Known limitation

These four commands are what the open designs actually use, so the suite tests clock and I/O constraint integrity — not timing-exception handling. Defects built on clock groups, false paths or generated clocks would have nothing to remove.

Task 2 · Create benchmark tasks

Could the agent have just looked up the answer?

Without randomised references, a correct submission proves nothing — because diagnosing the defect and retrieving the original file produce the identical answer.

That is the real argument, and it is stronger than "there might be leaks". Suppose the reference is upstream's own constraint.sdc, as it is by default. An agent that submits the correct period might have reasoned about the design — or it might have run cat on a file. The benchmark cannot tell the two apart, so it measures retrieval and reports it as engineering.

And the answer is easy to come by

These are open-source designs from a public repository. The correct constraints ship with the design, so they sit inside the very workspace the agent is working in — and, because the project is on GitHub, they are plausibly in the training data of any model being evaluated. That second channel is not a file, so no amount of directory cleaning touches it. It is the same contamination criticism levelled at SWE-bench.

Scrubbing the workspace is necessary but unfalsifiable — you can never prove you removed every copy, and it does nothing about training data. Randomising the reference is sufficient by construction: an instance that did not exist before we generated it cannot have been memorised, and every leaked copy of upstream's value is simply wrong.

It worked. The references for C1 were drawn as 0.69 and 0.58 — values that appear nowhere, keyed on a secret held outside the agent's reach. The agent recovered both exactly, with the leak audit clean. It could not have copied them; it had to recognise a ×1000 unit slip and invert it. That is the difference between a benchmark and a lookup.

Task 2 · Create benchmark tasks

Two benchmarks, and the structural difference between them

sdc-repair-v1 — HP-A

Task. One defect injected into the constraints. Diagnose and repair it; judged on the physical design that results.

Deliverable. An edited impl.sdc — the only file read.

FAIL_TO_PASS. signoff_setup_ws and signoff_setup_tns ≥ baseline, plus 9 PASS_TO_PASS gates.

knob-opt-v1 — HP-B

Task. Nothing is broken. Shrink the die by tuning flow knobs, inside a 12-run budget.

Deliverable. knobs.json — a knob-value map.

FAIL_TO_PASS. die_area ≤ baseline × 0.98, plus 11 PASS_TO_PASS gates.

Why optimisation needed a different grading shape

In repair, something is broken, so assertions flip fail-to-pass — that is what FAIL_TO_PASS means. In optimisation nothing is broken: every assertion passes at baseline, there is no flip to define, and left alone the null agent wins by changing nothing. Hence an improvement threshold. Two further departures, both forced by measurement:

  • area_not_ballooned is dropped — it caps area at baseline × 1.05, which is precisely what the benchmark asks the agent to change.
  • The timing gate becomes "still closes" rather than "no worse than baseline". Under the repair gate the true optimum fails over 5 ps while closing comfortably — optimisation is explicitly allowed to spend slack to buy area.

Both benchmarks are graded identically in one respect: the flow is re-run from clean with the submission, and the agent's own run directory is never trusted — the same reason SWE-bench re-runs tests from a fresh checkout.

Task 3 · Run a baseline

How a baseline agent run actually works

We run the real agent product — Claude Code — in unattended batch mode (claude -p "…"): no human watching, no interactive prompts. It receives the task text, works on its own, and stops when it is finished or runs out of turns.

1.  START      a throwaway container per instance: real OpenROAD toolchain,
               plus only the agent-visible files (impl.sdc, the task text)

2.  SANITISE   strip everything that leaks the answer — .git, stale results,
               the pristine SDC, rules-base.json, autotuner.json.  Audited.

3.  AGENT      it edits the SDC, runs `make` to build the chip, reads its own
               QoR, iterates.  Every action is logged to a transcript.

4.  STOP       whatever is in the deliverable file is taken as the submission.

5.  GRADE      a separate step the agent cannot touch: rebuild from clean with
               the submission, then re-time against the held-out reference.

6.  DESTROY    container discarded.  Nothing the agent did is trusted.

Why step 5 is separate. We never read the agent's own reported results. It could have hand-edited a metrics file or left stale artifacts behind, so the grader rebuilds the design itself. Because ORFS QoR is bit-exact deterministic — verified across thread counts on two platforms — that independent rebuild reproduces the agent's run exactly. No noise, no dispute, no tolerance band.

Each run leaves an audit trail: full transcript, the exact prompt sent, the submitted file, the leak audit, wall-clock, cost, and the reason the agent stopped.

Grading is behavioural, not diff-matching

C3 passed with a textually different fix. C5 submitted 0.35 where the reference was 0.15 — and passed, because its layout re-times as well as the reference's. The question is never "did you recover the reference value" but "is the design you produced as good".

That also settled a worry: I had flagged C5 as possibly requiring a lucky guess. It doesn't — the acceptable band is wide, and only the grader knows how wide.

The one failure was ours, not the agent's

C5 first ran a correct parameter sweep, hit its turn limit mid-search, and never wrote its conclusion back — so it was graded as the null agent.

A task-design defect. Two fixes: require writing best-so-far to the deliverable after every trial, and report why the agent stopped so truncation is never mistaken for a wrong answer. Re-run at the same budget: solved.

Task 3 · Run a baseline · knob-opt-v1 on nangate45/gcd

Shrinking the floorplan: a one-paragraph spec bug cost 33% of the objective

The optimisation benchmark on nangate45/gcd. The agent may tune eight permitted flow knobs; in practice CORE_UTILIZATION dominates — it sets how tightly the standard cells are packed, and therefore the die size. Five of the eight knobs are inert on a design this small.

succeeds — all gates pass flow dies (FLW-0024, global placement)

The −27.09% design is smaller and still correct

Shrinking a floorplan is only a win if everything else survives it. At CORE_UTILIZATION = 77 the design passes every gate: setup WS +0.0127 ns (still closes), setup TNS 0, hold WS +0.1114 ns, DRC 0, antenna violations 0, placement violations 0, and power improved 0.19%. Timing slack fell from +0.016 to +0.013 — spent, not lost, which is the trade the task explicitly permits.

The finding. The grader was fixed to accept any non-negative slack, but the prompt still said "no worse than baseline". Same agent, same 12-run budget; the only change was that paragraph. In v1 the agent had measured u74 at 24.3% with positive slack and deliberately rejected it to satisfy both readings of an ambiguous rubric — correct behaviour against the spec it was given.

A third failure mode, beyond "agent games the grader" and "agent finds the answer": the task description and the grader disagree. The most invisible of the three — every gate passes, the agent looks sensible — and detectable only against a measured reference optimum.

Task 3 · Run a baseline

What the baseline taught us about the benchmark

Why it succeeded

C1 is unambiguous once diagnosed, and randomisation forced reasoning over recall — the agent had to recognise a ×1000 slip, not remember a number.

On the optimisation task it ran a genuine search: probe, hit the cliff, back off, converge. It found the reference optimum in 11 of 12 runs.

Why it failed

Never on reasoning. Once on budget — truncated mid-sweep, submitted nothing — and once on our ambiguous spec.

Both were benchmark defects. Both are fixed, and both are more useful findings than the pass rate.

Improvements this drove

  • Task: require best-so-far checkpointing every trial, so a truncated run degrades gracefully instead of submitting nothing.
  • Harness: report why the agent stopped — a 3/4 that hides a truncation is a dishonest number.
  • Grader: match the timing gate to the problem class — "restore baseline" for repair, "still closes" for optimisation.
  • Spec: state the gate in the prompt using the grader's exact words. Drift between them is invisible and expensive.

The cost asymmetry is a finding, not a footnote

Task shapeWall CostBudget behaviour
Repair (C1, C3)~140 s~$0.22 comfortable
Search (C5, knob-opt)~1000 s$0.85 – 2.39 consumed in full, every single time

Search is ~7× the wall time and ~6× the cost of repair. That is the argument for making run budget an explicit, graded dimension — and at hours per run on a real block, it is the business model rather than a detail.

Task 4 · Motivate the future product

Four capabilities, one substrate

① Constraint Guard · grader built

CI gate. Every SDC pull request is re-timed against sign-off constraints the author does not control.

PR #412  "tighten IO budget"        ✗ BLOCKED
Author reports:  WS 0.068 → 0.072  ▲ better
Sign-off says:   WS 0.068 → −0.280 ▼ FAILS
ⓘ deletes set_input_delay — input paths
  are no longer being checked at all.

② Closure Copilot · grader built

Proposes configurations, runs them under budget, presents a Pareto board for human approval, with the search trace and the cliff location shown alongside.

The comparator that would make it credible: ORFS ships AutoTuner, a real non-LLM optimiser over the same knob space. The claim to earn is not "we found −27%" but "we matched AutoTuner in 11 runs and explained why." A Bayesian optimiser cannot tell you the cliff is at 78 because of FLW-0024.

③ QoR Bisect · defined

Attributes a regression to a stage, then a cause — separating causal from inherited deltas.

synth      +0.0%  ·
floorplan  +8.1%  ████  ← first appears
place      +8.1%  ████  (inherited)
route      +8.2%  ████  (inherited)
ROOT: CORE_UTILIZATION 60→55, commit a3f21c

Only sound because QoR is bit-exact deterministic — every delta is attributable.

④ Budget Broker · defined

Allocates interface budgets across blocks and re-negotiates as blocks report back what they can achieve.

reg2out(A) + interconnect + in2reg(B)
                   ≤ period − uncertainty

allocated 480 ps > 450 ps budget  ✗ −30 ps
⚠ Every block closes. The chip does not.

The top-tier check is arithmetic — verifiable by hand in ten seconds, which is what you want in a gate a lead engineer signs.

Next: treat suspicious improvement as a review trigger, not a win

The repair gate asks "is sign-off timing no worse than baseline?". That is the right question for a regression, but it is one-sided: a run that comes back dramatically better passes silently. And on a repair task, where the reference is a known-good design, a large unexplained gain is as suspicious as a loss. It usually means one of:

  • the reference constraints do not fully pin the design, so the agent found genuine slack the benchmark never intended to offer;
  • the agent found a loophole the gates do not yet model;
  • the instance is mis-specified — the same class of error that made a spec ambiguity cost 33% of the objective.

The fix is a per-metric improvement band: a delta beyond which the run is not auto-passed but flagged for human review, shipped with its diff, its sign-off delta and its search trace attached. Cheap to add — the numbers are already computed — and it is what an engineer would do anyway. Nobody accepts a surprise 30% win without asking where it came from.

The mechanism generalises. The objective and the defect class do not. A suite that assumes one class or one objective fits every design will silently ship vacuous instances — which is exactly what per-instance validation is for.

One of the fourteen findings is a pure negative — a silent corruption channel with no measurable consequence, cut as a defect class. Five more overturned a design choice: an inert defect class on gcd, an untunable objective, two wrong guessed ranges, and a spec that disagreed with its own grader. They are in the repo on purpose — they are the reason the remaining claims are worth believing.
